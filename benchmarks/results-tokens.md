Generated by `./benchmarks/tokens.sh` on 2026-11-23 on the v1.1.2 tree: `main` at `6f0225d` with the second review round's changes (EST-8250) applied, before they merged. The `/usr` rows match the earlier v1.1.2-candidate run exactly; the `internal/` `search-code` row moved because that change added code. Only that row can move between this run and the tag, and only if `internal/` changes again. Tokenizer: tiktoken `o200k_base`. The previous run, at `9a4f8c7` on 2026-10-31, predates v1.0.0 and capped the `search-code` rows at 1000 matches.

Machine: Intel Xeon W-2295 (36 threads), 141 GB RAM, Debian 13 (trixie) container on Linux 7.0, x86_64.
The `/usr/bin` and `/usr/share` rows depend on what that machine has installed, so
they are not comparable with a run on a different system. Only the `search-code`
and `read-file` rows on `internal/` are machine-independent: `list-directory` and
`get-directory-tree` print directory sizes and timestamps, which vary with the
filesystem.

Baseline is `--full --format json`, which is byte-identical to the pre-AXI `--json` output for every command this benchmark runs. "reduction" is the default mode (minimal fields, TOON) against that baseline.

The script passes `--max-results 1000000` to `search-code`, so every row lists
every match: at the default cap of 1000 this row (1124 matches) measured a
truncated list.

The binary absolutizes `--path` and echoes the absolute checkout path in this
table's output (once per match for `search-code` - 1124 times), which would
otherwise move every count with the length of the reader's checkout path: the
same run measures thousands of tokens more from a deeply nested pipeline
worktree than from a short `~/src` clone. The script therefore replaces the
checkout prefix with the fixed placeholder `/repo` in the captured output
before counting, so these are the figures any reader measures, wherever their
clone lives.

## Why `json-min` can exceed `json-full`

Two commands can print a larger `json-min` than `json-full` in the tables above:
`search-code` on every target, and `get-directory-tree` on a target where its
minimal projection saves less than the payload it adds (`/usr/bin` here). Both are expected, not a
defect.

### `search-code`

`search-code` already emits its minimal field set at full size. In the benchmarked
invocation every match carries exactly `content`, `file` and `line` in both modes,
and the 1124 match items on this repository's `internal/` hold identical values in
both modes, serialized in a different key order, so there is nothing for the minimal
projection to remove. With `--context N` both modes carry each match's `context`
field as well - the minimal projection keeps it whenever `--context` asked for it,
which is the fix that regenerated this file - so the projection removes nothing in
that case either. For this command there is no invocation in which the projection
removes anything.

What minimal does add is the `next_steps` payload, 149 bytes in the benchmarked
invocation, which `--full --format json` deliberately omits so it stays
byte-identical to the pre-AXI `--json` output for this command. With `--context` the payload is
smaller, because the next_steps hint naming `--context` is suppressed once context
was requested, but minimal remains the larger of the two there as well. So for this
one command minimal costs slightly more and saves nothing in every case, and the
reduction reported in the table above comes entirely from TOON encoding rather than
from field selection.

Changing this would mean either dropping contextual disclosure from minimal JSON or
breaking the legacy guarantee on `--full`. Neither is worth 149 bytes.

### `get-directory-tree`

For the tree rows, compare the two JSON columns: `internal/` is json-min 213 against
json-full 221, and `/usr/bin` 96 against 70. Two things move in opposite directions.
The minimal projection drops each child node's `path` — the root keeps `path: "."` —
so on `internal/` it removes `filesystem`, `filesystem/commands`, `filesystem/core`
and `filesystem/mcpserver`. Minimal also adds the `next_steps` payload that
`--full --format json` deliberately omits: 86 bytes of *Add --full for all fields
(path, mode, timestamps, ...).*. Where there are few paths to drop the hint is
worth more than they were. `/usr/bin` is flat, so its tree is a single node and no
child path is dropped at all: minimal there is exactly the 86-byte hint and 26
tokens larger. `internal/` now has four paths to drop, which more than pays for the
hint: the document is 70 bytes and 8 tokens shorter. On a tree with more than a
handful of directories the projection wins outright (`/usr/share`: 18262 against
json-full 25580), and that is where the reduction in the table comes from.
