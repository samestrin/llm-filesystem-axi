# AXI audit: `llm-filesystem` against the ten principles on axi.md

- **Audited:** 2026-11-20, on a `make build` of tag `v1.1.1` at `43fd800` (EST-7786). Line numbers are at that commit. Between `v1.1.0` and `v1.1.1` the only code changes were the `batch-file-operations` help text and `--json=false` handling in `output.go`; no cited line moved, and every probe below gave the same result.
- **Method:** by hand. `axi-axi` is not installed on the build host. Each principle was checked against the text on https://axi.md, by running `build/llm-filesystem` in a scratch directory and reading the code the output comes from.
- **MCP server:** `llm-filesystem-mcp`, a thin MCP stdio server, ships beside the CLI (epic 09, first released in `v1.1.0`). Every tool is one CLI command: the server runs the `llm-filesystem` binary and returns its output, and a failing command comes back as an MCP error carrying the CLI's own error and exit code, never as a success. The verdicts below are about the CLI and carry over to the server, because every tool result is the CLI's own output. Probed: `tools/list` returns 28 tools, and llm_filesystem_read_file on a missing path returns `isError: true` with the CLI's TOON error and `exit_code: 1`.
- **Result:** all ten principles met, two of them with a stated exception: principle 7 (no session-end capture) and principle 6 (`write-file` replaces an existing file without `--confirm`). Each is listed under "What remains" with its reason.

## What remains

- **No session-end capture** (principle 7). Reason: this CLI keeps no session history, so a session-end hook would have nothing to capture; keeping history is out of scope for a filesystem tool. Stated identically in the README's Limits and the catalog entry's `exception`, and guarded by `TestSessionEndGapStatesItsReason` and `TestReadmeLimitsGapsMatchCatalogException`.
- **`write-file` replaces an existing destination without `--confirm`** (principle 6, whose "never prompt" rule the `--confirm` gate implements). Epic 10 T5 kept this behaviour while gating delete, move/copy onto an existing path, and destructive batch entries. Stated in the README's Limits and the catalog `exception`; the behaviour is pinned by `TestWriteFileStillReplacesWithoutConfirm`.

### Principle 6 in detail (v1.0.0)

- **6a. `compress-files` and `extract-archive` reported partial work as success.** Probed on the v1.0.0 binary:
  - `llm-filesystem compress-files --output out.zip --paths a.txt,missing.txt` prints `files_added: 1`, `success: true` and exits 0, with no mention that `missing.txt` was never added. The archive exists and holds only `a.txt`.
  - `extract-archive` had the same failure class: entries not written were not reported, and a partial run exited 0.

  This is the partial-failure finding epic 04 was created for, and it is the reason the "nothing may report success when it did not succeed" rule exists. Closed on `main` by epic 04: `fix(extract-archive): report every entry not written; exit 1 on a partial run` (`#24`) and `fix(compress-files): report every input not added; exit 1 on a partial run` (`#25`), with docs in `#27` and an end-to-end test in `#28`. The fixes are **not** in the audited v1.0.0 binary; they shipped in v1.0.1.

- **6b. `create-directory` on an existing directory reports `created: true`.** Probed: a second `create-directory --path <same dir>` prints `created: true` / `Directory created successfully` and exits 0, though nothing was created. The mutation itself is idempotent (`os.MkdirAll`, `internal/filesystem/core/write.go:337-338`), but the report claims work that did not happen — the same failure class as 6a. Still present on `main` at the time of the audit; neither epic 04 nor 05 had a task for it, so it was filed as tech debt (TD #39). Fixed after the audit (PR #38): `CreateDirectory` checks for the directory before `MkdirAll`, and a repeat run now reports `created: false` / `exists: true` with `Directory already exists: <path>`. Like 6a, the fix is **not** in the audited v1.0.0 binary; it shipped in v1.0.1.

Idempotency of the remaining mutations was spot-checked, not exhaustively probed: `delete-file` without `--confirm` changes nothing (probed).

- **6c. `delete-file` on a path that was already gone exited 1** with `error: true` / `path does not exist`, though the state asked for already held. Found by the 2026-11-16 fresh-context review (EST-6608) and fixed on `main`: it now exits 0 with `deleted: false` / `existed: false`, alone or as a `batch-file-operations` entry; a missing parent directory or a path outside `--allowed-dirs` is still an error. Guarded by `TestDeleteFileOnAMissingPathIsANoOp`, `TestDeleteFileStillFailsForAMissingParentOrOutsideAllowedDirs` and `TestBatchDeleteOfAMissingPathIsANoOp`.
